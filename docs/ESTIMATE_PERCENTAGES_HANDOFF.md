# Проценты по разделам сметы: памятка для разработчика React Native

Подготовлено 1 ноября 2026 года по текущему веб-прототипу ЗАМЕРX.

## Что требуется

У каждой сметы сохраняются независимые проценты для материалов, работ и оборудования. Положительное значение — наценка на базовую стоимость раздела, отрицательное — скидка. Экран расчёта, общая сумма объекта и документ клиента должны использовать согласованный расчёт.

Это описание поведения веб-прототипа и основа для интеграции. Код отдельного React Native приложения, его API и схема серверной базы в этой проверке не исследовались. Оценивать срок их изменения по прототипу нельзя.

## Что уже готово

Пути ниже указаны относительно `Проект/app`.

| Файл | Что можно использовать |

| `src/utils/estimate-export.js` | Чистые JS-функции: подготовка строк документа, распределение копеек, включение процентов в цены, разделение общей сметы по помещениям |

| `tests/estimate-adjustment.test.mjs`, `tests/estimate-export.test.mjs` | Проверки расчётного ядра и подготовки экспорта |

Первые два модуля не используют React, DOM, сеть или базу данных. Они подходят как основа общего расчётного ядра; совместимость конкретной версии JS-движка мобильного приложения и форматирования чисел нужно проверить на устройствах. Браузерные функции скачивания, отправки и создания PDF из `src/design-bridge/estimate-entry.js` требуют отдельной мобильной интеграции.

## Формат данных в прототипе

```json
{
  "estimateAdjustment": {
    "scope": "works",
    "percent": 10,
    "rates": {
      "mats": -5,
      "works": 10,
      "equipment": -10
    }
  },
  "estimateExportOptions": {
    "showAdjustment": true
  }
}
```

- `rates` — все три сохранённых процента. Выгрузка учитывает их все, независимо от последнего открытого раздела.
- `scope` — выбранный раздел интерфейса; `percent` — его отображаемое значение. При разных процентах и `scope: "all"` поле `percent` равно нулю и не означает отсутствие корректировок: расчёт использует `rates`.
- В текущем интерфейсе «Вся смета» при вводе значения заменяет все три процента одним значением. Дополнительная общая наценка поверх трёх процентов не применяется.
- Отсутствующий объект означает отсутствие корректировки. Старый формат `{ "scope": "works", "percent": 10 }` поддерживается отдельно, без обязательной массовой перезаписи проектов.
- `showAdjustment` управляет представлением документа: отдельные строки корректировок либо включение процентов в цены. Общая сумма от этого не меняется.

В прототипе объект принадлежит проекту. В мобильном приложении с несколькими сметами или версиями на один объект проценты должны принадлежать соответствующей смете/версии. Базовые цены и количества остаются отдельно от процентов.

## Что подключить в мобильном приложении

1. Найти владельца данных сметы и текущий путь сохранения: UI → локальное хранилище → API → серверная база → загрузка. Передавать новые значения через каждый используемый слой, включая сериализацию, валидацию и синхронизацию.
2. Выбрать хранение под существующую схему: например, три числовых поля или объект настроек в существующем документе/JSON-поле. Это варианты, а не готовая миграция: потребность в миграции определяется реальной базой. Новые таблицы для каждой позиции из самой этой функции не следуют.
3. Подключить единый согласованный расчёт к экрану сметы, карточке объекта, документу клиента и договору, если он есть. Если итог проверяет сервер, сервер должен применять те же правила и округление.
4. Сохранить исходные цены. Повторный пересчёт или открытие сметы не должны начислять процент ещё раз на уже изменённую цену.
5. Адаптировать подготовленные строки к существующему механизму PDF/другой выгрузки. Если документ делится по помещениям, распределять подготовленную общую смету с сохранением её копеек, а не независимо округлять каждое помещение.
6. Проверить создание, редактирование, копирование и восстановление сметы; повторную загрузку с сервера; сценарии офлайн, если они поддерживаются; поведение уже выданных документов согласно существующей политике версий.

Хранение исходных данных и процентов позволяет пересчитать итог. Если приложение уже сохраняет рассчитанные итоги или снимки документов, их обновление и версионирование нужно встроить в существующий процесс; удалять этот механизм ради новой функции не требуется.

## Контрольный пример

| Раздел | База | Процент | Изменение | После корректировки |
| --- | ---: | ---: | ---: | ---: |
| Материалы | 10 000 ₽ | −5% | −500 ₽ | 9 500 ₽ |
| Работы | 20 000 ₽ | +10% | +2 000 ₽ | 22 000 ₽ |
| Оборудование | 5 000 ₽ | −10% | −500 ₽ | 4 500 ₽ |
| Итого | 35 000 ₽ | — | +1 000 ₽ | 36 000 ₽ |

При смене выбранного раздела, сохранении/загрузке и смене способа отображения процентов итог остаётся 36 000 ₽. Суммы строк, разделов, помещений и документа должны сходиться по согласованным правилам округления.

В текущем ядре одинаковые проценты трёх разделов округляются как корректировка всей сметы; разные — по разделам. Это существенно на суммах с копейками. Правило стоит сохранить при переносе либо отдельно согласовать изменение.


Результат: 89 тестов прошли, 0 ошибок. Проверены независимые проценты, скидки, старые проекты, локальное сохранение/восстановление, отображение корректировок в ценах и строками, копейки, распределение по помещениям, согласованность сметы и договора. Это проверки веб-кода в Node.js, не проверка серверной базы и не запуск на iOS/Android.

## Что нужно для точной оценки и готового патча

- Модель сметы и соответствующий фрагмент схемы базы/миграций.
- Код чтения и сохранения сметы, включая API и локальное хранилище.
- Текущие расчёт и генератор документа.
- Версии React Native и используемого JS-движка; наличие офлайн-синхронизации и версий документов.

Секреты, пароли и реальные данные клиентов для этой работы не нужны. После просмотра этих частей можно подготовить изменения под действующую архитектуру и оценить оставшуюся интеграцию.

## Решения, которые стоит сверить с мобильным приложением

- Действительно ли речь о наценке на базовую стоимость, как в прототипе, а не о марже от конечной цены.
- Сохраняется ли правило «Вся смета заменяет три процента», без дополнительного начисления поверх них.
- Подходит ли существующая политика округления и отображения процентов в документе.
- Подходит ли диапазон прототипа: от −100% до +1000%. В ядре некорректные значения нормализуются; в API нужна явная проверка входных данных по правилам приложения.
